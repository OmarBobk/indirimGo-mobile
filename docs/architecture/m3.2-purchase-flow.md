# M3.2 Flutter Buy-Now Purchase Flow

## Scope

Single-line / buy-now wallet purchasing for the authenticated customer Android
client:

- Product selection from package detail
- Fixed quantity or custom amount
- Sanitized package requirements
- Server quote (`POST /checkout/quote`)
- Checkout review with authoritative totals and wallet affordability
- Wallet confirm (`POST /checkout`) with required `Idempotency-Key`
- Unknown-result recovery (`GET /checkout/status`)
- Durable owned receipt (`GET /orders/{order_number}`)
- Wallet available-to-spend (`GET /wallet/summary`)

## Exclusions

- Multi-line cart, cart icon, cart persistence, server cart
- Wallet top-up
- Full order history
- Fulfillment tracking, refunds, notifications/realtime UI
- Client pricing / trusted money math
- Contract endpoints, production deploy, APK publish
- Flutter code generation / new state-management frameworks
- New authentication behavior beyond existing session rejection

## Architecture

Feature-first Riverpod (no codegen) + go_router + single Dio client:

- `lib/features/purchase/` — draft, quote, checkout, recovery, receipt
- `lib/features/wallet/` — wallet summary for Account / checkout surfaces
- Catalog `Money` reused; amounts remain decimal strings
- `PendingCheckoutStore` keeps **per-customer** recovery records containing
  only: customer id, unresolved Idempotency-Key, optional completed
  `order_number` anchor, and created-at (secure storage in production,
  in-memory fake in tests). Never requirement values, payloads, fingerprints,
  prices, or receipt bodies.

## Idempotency lifecycle

1. Resolve key: in-memory active → same-customer stored unresolved key → else
   generate with `Random.secure()` (`ig-` + base64url entropy, ≤128 chars).
2. Persist the unresolved key to the customer-scoped record **before**
   `POST /checkout`. Never overwrite a different unresolved same-customer key.
3. Reuse the same key for in-session identical-payload retries
   (`checkout_retry_required`). Unknown/network results route to recovery —
   recovery owns the attempt (confirm disabled).
4. On success (confirm or status completed), durable ordering is:
   validate receipt → `markCompleted(order_number)` while key exists →
   establish in-memory success/receipt → `clearPendingKey` (keep anchor) →
   navigate/render receipt → clear anchor only after explicit Done/Home.
5. Safe terminal abandonment (`price_changed`, `purchasing_unavailable`,
   failed/not-found/restart-required) clears only that customer's record.
   Logout/customer switch clears in-memory UI only — never another customer's
   recovery record.

## Unknown-result recovery

On authenticated startup, after session restoration:

1. Read **this customer's** recovery record only (never delete others).
2. If a completed `order_number` anchor exists, `GET /orders/{order_number}`,
   show receipt, keep anchor until Done.
3. Else if an unresolved key exists, call `GET /checkout/status` with
   `Idempotency-Key` header.
4. Handle completed / processing / retry-required / failed / not-found /
   offline / auth rejection with the same durable success ordering.

Polling is bounded (`checkoutRecoveryMaxPolls`), cancellable, non-overlapping,
and respects server `retry_after_seconds`. Manual retry is always available.

After application restart, requirement values are gone. For
`checkout_retry_required`, clear that customer's pending key and require the
customer to restart the purchase form. Do not recreate the payload.

## Requirement privacy

- Requirement keys are server identifiers.
- Labels/options are server catalog content.
- Values never appear in model `toString`, exceptions, logs, receipts, or
  pending storage.
- Unsupported/unsafe schema fails closed to a localized purchase-unavailable
  state.

## Money rules

- Keep `amount` as a decimal string.
- Render only server `display.formatted` where available.
- Render all money text LTR, including inside Arabic screens.
- Never parse trusted totals into `double`.
- Never multiply price × quantity or compute subtotal/discount/affordability/
  conversion/final total locally.

## Routes

Protected under `/app`:

- `/app/packages/:id/buy?productId=`
- `/app/checkout/review`
- `/app/checkout/recovery`
- `/app/orders/:orderNumber`

## Local M3.3 run instructions

Prerequisites: Flutter 3.44.8 / Dart 3.12.2, Laravel `origin/staging` served
locally with migrations.

```powershell
php artisan serve --host=0.0.0.0 --port=8000
flutter pub get --enforce-lockfile
flutter run --dart-define=API_BASE_URL=http://10.0.2.2:8000/api/v1
```

Walk the buy-now path against a customer with wallet funds, then force a lost
checkout response and confirm recovery via `GET /checkout/status`.
